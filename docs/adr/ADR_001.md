# ADR-001 Message Queue Selection

## Status
Accepted

## Date
2026-04-26

## Context
notify-engine is a high-throughput notification system that must process multiple event types across different notification channels — email, SMS, and in-app. Each event type requires independent processing by dedicated consumer services. The system must handle sustained high volumes approaching 1 million events, maintain ordered processing per user to prevent out-of-sequence notifications, and guarantee that no duplicate notifications are delivered to end users. We need a message queue that supports async decoupling between the API gateway and notification dispatchers, scales horizontally without becoming a bottleneck, and provides replay capability for failed events.  

## Options Considered: 
### Kafka
Apache Kafka is a distributed event streaming platform designed for high-throughput, fault-tolerant message processing. In production at Accenture, we used Kafka to handle multiple event types across pipeline workflows — producers published events to topics and consumers processed them independently based on topic subscription, with events queued and processed sequentially as consumers became available. Kafka's strength is its ability to handle millions of events with ordered processing per partition, persistent message storage, and replay capability. Its weakness is operational complexity — it requires additional infrastructure including Zookeeper or KRaft, careful partition configuration, and more DevOps overhead compared to simpler alternatives.  

### RabbitMQ
RabbitMQ is a traditional message broker that routes messages between producers and consumers using exchanges and queues. Its strength is simplicity — it is easy to set up, supports flexible routing patterns, and works well for task queues where each message is processed once. Its weakness for notify-engine is that messages are deleted after consumption, making replay impossible. At the scale of 1 million plus events, RabbitMQ also requires significant tuning and clustering to remain stable, adding complexity without the throughput guarantees Kafka provides natively.  

### BullMQ
BullMQ is a Redis-based job queue library for Node.js designed for background job processing. Its strength is simplicity of integration — it requires no additional infrastructure beyond Redis, which notify-engine already uses for deduplication, and it has excellent Node.js support. Its weakness is that it is designed for discrete jobs rather than event streams. It does not support ordered processing per entity, partition-based parallelism, or native replay of failed events. At 1 million plus events it would place extreme memory and throughput pressure on Redis, creating a bottleneck in the same layer we rely on for idempotency.  

## Decision
Kafka  

## Rationale
Kafka was selected because it directly satisfies the three core requirements of notify-engine. First, its partition-based architecture allows us to key messages by user_id, guaranteeing ordered processing per user while maximizing parallel throughput across partitions. Second, its persistent log storage enables replay of failed events without any additional infrastructure — a requirement that eliminates RabbitMQ from consideration. Third, Kafka's consumer group model allows independent scaling of email, SMS, and in-app dispatcher services without coupling — each consumer group reads from the same topic independently at its own pace. BullMQ was eliminated because placing 1M plus events through Redis would create a bottleneck in the same layer we rely on for idempotency, and it lacks native support for ordered per-entity processing.  

## Consequences
Easier: The system can scale horizontally by adding partitions and consumer instances without architectural changes. Failed events can be replayed from the Kafka log without a separate storage layer. Each notification channel scales independently.  

Harder: Local development requires running Kafka and Zookeeper via Docker, adding infrastructure overhead. Operational knowledge of partition strategy, consumer group offsets, and lag monitoring is required from day one. The learning curve is steeper than BullMQ for engineers new to event streaming.
